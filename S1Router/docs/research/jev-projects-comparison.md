## What the projects are

LocalJev is a Bun/TypeScript HTTP bridge. It accepts a Jev-style `POST /v1/systemone`, translates typed questions into an OpenAI-compatible classification prompt, asks a local endpoint for JSON probabilities, validates the response, retries malformed JSON, and converts it back to Jev answer shapes. The source verifies JSON-schema prompting, deterministic request-derived seeds, output parsing, probability range checks, positive-sum normalization, first-presented-option tie breaking, index-based score expectations, and inverse-entropy confidence ([engine](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/src/engine.ts), [tests](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/test/engine.test.ts)). The server verifies optional bearer authentication, health/readiness/model routes, request validation, error mapping, and bounded in-flight/queued calls ([server](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/src/server.ts), [config](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/src/config.ts)).

The README calls the result “wire-compatible” but explicitly says the prompted probabilities are not mathematically equivalent to OpenJev's direct logit read and should be calibrated on the target workload before consequential use ([README](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/README.md)). The source and evaluation guide therefore support treating LocalJev as a provider bridge with raw or unavailable calibration status, rather than as a calibrated S1M model.

jev-align is an experimental Python CLI for interactive AI Function alignment. It reads CSV, Parquet, or JSONL rows, evaluates a fixed task definition through a TypeSafe, Vercel, or Cloudflare adapter, selects uncertain rows plus a seeded exploration row, collects human labels and optional rationales, proposes text-definition changes through GEPA, and requires a human accept/reject decision before the next candidate becomes current ([README](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/README.md), [acquisition](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/acquisition.py), [session](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/session.py)). Its persisted run records source hash, selected columns, backend/model, candidate history, labels, reports, and rewinds ([models](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/models.py), [persistence](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/persistence.py)).

The README's “calibrated classifiers” wording is broader than the implementation evidence. jev-align consumes provider probabilities/confidence and scores definitions; it does not fit a calibration profile, train a local checkpoint, or export an immutable model bundle. It also supports multilabel tasks, which are outside decision-v1's current Choice/Bool/Score kinds.

## Overlap with S1Router and S1M

| Area | LocalJev | jev-align | S1 consequence |
| --- | --- | --- | --- |
| Typed finite decisions | Jev `noul`, choice, and score request/answer shapes; score values are array indices | Binary, multiclass, multilabel, and ordered Score candidate definitions | The shape is conceptually close to decision-v1, but `noul` is not the contract's `bool`, and index scores cannot silently become sparse integer Score levels. Use an explicit adapter. |
| Input and output boundaries | Validates request/question shape and complete answer keys; rejects non-finite/out-of-range numeric output | Pydantic validates task/prediction shape and candidate component sets | Supports R-001/M-005-style boundary testing, but neither provides the full contract's unknown-field, duplicate-key, byte/depth, task-hash, provenance, or policy checks. |
| Uncertainty | Inverse entropy for choice/score; README and source warn it is not correctness probability | Ambiguity acquisition from probability/confidence; binary/multilabel thresholds use 0.5 | Useful acquisition signal, not automatic acceptance evidence. S1 must keep `confidence` distinct from calibrated acceptance probability. |
| Bounded execution | Configurable in-flight semaphore, queue cap, per-upstream timeout, malformed-output retries, readiness endpoint | Async provider concurrency; gateway calls have a 60-second timeout; bounded local capture queue/file limits | Good patterns for R-009/R-011 and L1/L2 NFRs. They do not supply S1's monotonic deadline settlement, budget reservation, circuit breaker, or mandatory audit behavior. |
| Evaluation loop | Reproducible, hashed bake-off manifest; records per-attempt timing, retries, failures, Brier/NLL/ECE and Wilson intervals | Active acquisition, human labels, optional holdout, candidate diff/history, GEPA budget, replay caches, accept/reject/rewind | LocalJev informs provider screening; jev-align informs L4 annotation UX. Neither meets the S1 final-test risk/coverage gate by itself. |
| Persistence and operation | HTTP server only; no decision audit/replay or model artifact lifecycle | Durable labels and state, atomic state/capture snapshots, archived rewinds, optional production capture | jev-align's run history is a useful research artifact pattern; S1 still needs its own redacted audit records, artifact manifest, rollback and retention semantics. |
| Provider boundary | One OpenAI-compatible local upstream; no router policy | Provider protocol with TypeSafe/Vercel/Cloudflare adapters and separate reflection model | Both reinforce ports/adapters. Keep provider access outside router policy and keep reflection/evaluation providers outside S1M inference. |

## Requirement-linked gaps and risks

### LocalJev against S1Router

LocalJev partially exercises R-001, R-003, R-005, R-007, R-009, R-011, and R-013, but it is not an implementation of those requirements. The important gaps are:

* Its request schema has only `state`, `model`, and `questions`; it has no S1 request ID, data class, language declaration, task/version/definition hash, deadline, remote permission, cost ceiling, policy snapshot, or audit reference. The validator also does not enforce S1's unknown-field, duplicate-key, byte-size, nesting, or 1–32-question contract rules ([types](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/src/types.ts), [decision-v1](../contracts/decision-v1.md)).
* It accepts a choice with 2–128 options and a score with 2–10 criteria, whereas the S1 contract has lower, typed support limits and exact registered task identity. It silently converts a score's position to the expected value; S1 Score uses the declared integer values, which may be sparse ([engine](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/src/engine.ts), [decision-v1](../contracts/decision-v1.md)).
* `normalizeDistribution` accepts any positive-sum vector and rescales it. That is useful for a tolerant bridge, but it is weaker than decision-v1's complete distribution and sum tolerance. Normalization must not be recorded as calibration and must not turn a malformed or self-reported vector into an accepted local answer.
* The engine retries malformed model JSON, but a group failure raises an error for the whole decision. It does not implement S1's one terminal outcome per question with failure isolation, ordered finite provider fallback, atomic request budget, cancellation settlement, or circuit breaker. Groups are processed sequentially even though each group is bounded by question/outcome counts.
* The server's default host and upstream are loopback, but the upstream receives the serialized state. There is no S1 data-class policy, redaction, endpoint allowlist, audit write, replay record, or retention policy. Optional API-key authentication protects the bridge endpoint only; it is not data authorization.
* The README system prompt asks the model to “return calibrated probabilities,” while the README also warns the values are generated/self-reported. The evaluation guide correctly says inverse-entropy confidence is not correctness probability and says the results are not a calibration certificate ([evaluation guide](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/docs/evaluation.md)). Treating LocalJev's `confidence` as S1 R-004 evidence would be a contract error.

The evaluation framework is a strong screening harness but not release evidence for the S1 target. It uses 40 examples per task in the published matrix, one question/request and one in-flight request, and explicitly labels the result a prompted-probability screening sample. It hashes data/code inputs, records failures and retries, and calls out missing model-weight/runtime pinning and possible public-data contamination ([evaluation guide](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/docs/evaluation.md), [results](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/docs/evaluation-results-2026-09-18.md)). It does not produce S1's 200 accepted final questions, one-sided accepted-error bound, calibration identity, task slices, artifact evidence, offline/privacy drill, or router overhead measurement.

### jev-align against S1M

jev-align partially informs M-001, M-003, M-004, M-008, M-010, and M-012, and is especially relevant to a future L4 annotation workflow. Its limits are material:

* Candidate models preserve the task kind and fixed class/label names while GEPA changes instructions and criteria. This is a useful guard against accidental label-set mutation, but it is not the task registry, canonical definition hash, or immutable model/preprocessor/calibration identity required by M-001 and decision-v1 ([models](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/models.py), [optimizer](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/optimizer.py)).
* The optional 20% holdout is selected and scored separately, but `optimize_candidate` passes the same labeled training examples as both GEPA `dataset` and `valset`. The holdout is evaluated after optimization in `ClimbSession.optimize`; it does not control GEPA's candidate search. This is acceptable as an interactive alignment loop only if described as such, and it cannot substitute for M-003/M-008's untouched final test.
* There is no dataset provenance/license/label-origin gate, duplicate or repository-lineage split, two-reviewer adjudication, calibration fit, immutable model artifact, offline runtime, resource release gate, or quantization re-evaluation. The source hash protects the selected source file from accidental changes; it does not establish source rights or leakage resistance.
* The provider adapters classify TypeSafe binary values as `calibrated_probability` and multiclass/Score values as `native_confidence`, but the adapter code validates ranges/shapes rather than independently establishing calibration. It also does not bind probabilities to an S1 task definition hash or verify every response key and distribution against the registered support ([backends](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/backends.py), [TypeSafe adapter](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/jev.py), [gateway adapter](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/jev_gateways.py)).
* The production capture helper writes input fields and predictions to local JSONL files. It bounds queue/record/file sizes and counts drops, but it intentionally does not fsync the request path and says buffered records may be lost. Captured input is therefore both a privacy/retention concern and an incomplete audit record until S1 redaction, consent, retention, access control, and durability requirements are applied ([capture](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/capture.py), [runtime](https://github.com/sutro-sh/jev-align/blob/49753df924d30c0d3642b58e0b9b1e89921dc102/src/jev_align/runtime.py)).
* GEPA receives row-level feedback containing state, predicted/expected labels, and human rationale in the evaluator payload. Whether the selected GEPA reflection provider is local or remote is configurable. This must be treated as an outbound data processor under S1's data policy; “production learning” is not automatically an offline or private workflow.

## Reusable ideas and code

The safest reuse is conceptual and test-oriented:

* From LocalJev: put an untrusted document in an explicit prompt boundary; keep caller question IDs out of the model prompt and use internal positional IDs; derive repeatable request seeds; enforce a strict response schema; keep malformed-output correction bounded; expose readiness separately from liveness; and include retry/failure/token telemetry in evaluation records.
* From LocalJev's evaluation harness: make experiment manifests resumable and immutable by hashing the suite, code, configuration, and sampled IDs; retain failed attempts in timing statistics; report valid-only and effective accuracy separately; and state exactly what the benchmark does not establish.
* From jev-align: separate evaluation-provider ports from the domain loop; use uncertainty plus random exploration instead of uncertainty-only acquisition; persist candidate diffs and human rationales; keep a pending candidate until an explicit accept/reject decision; archive rewinds; and separate production capture from labels and alignment-run state.
* Do not copy either project's prompt wording, wire adapters, or persistence files into the S1 domain without contract tests. LocalJev's normalization/confidence semantics and jev-align's provider vocabulary are not decision-v1 semantics.

Code reuse is legally possible in principle, subject to review. LocalJev's MIT license requires retaining its copyright/license notice. jev-align's Apache-2.0 license permits modification and redistribution subject to its license, notice, attribution, and modified-file conditions; it does not grant TypeSafe, gateway, model, or dataset rights. Neither upstream license relicenses the dependencies or data they call. In particular, LocalJev's evaluation guide identifies BoolQ as CC BY-SA 3.0, says AG News has an unknown/research/non-commercial licensing situation, and says the SST-5 mirror has no stated license; those datasets and their text must not be copied into S1 evidence or training without a separate provenance decision ([dataset notes](https://github.com/githubnext/localjev/blob/3f23e36e1a3bff46c7e83e8e3781d3512bc82021/docs/evaluation.md)). jev-align's `pyproject.toml` uses broad dependency ranges, so adopting code would require new exact pins, lockfile entries, and transitive license/security review under [delivery controls](../engineering/delivery.md). No model weights or captured production inputs should be imported from either project.

## Recommended documentation changes

These are precise proposed edits for a later owner-reviewed change. They do not claim that any requirement is implemented.

1. Add two pinned entries to [docs/sources/README.md](../sources/README.md): `JEV-LOCAL` for LocalJev at the revision above, described as a prompted-probability bridge and evaluation-harness reference; and `JEV-ALIGN` for jev-align at the revision above, described as an interactive human-feedback/prompt-optimization reference. Record retrieval date, license, and the limits above. Do not add their benchmark datasets or model claims as S1 evidence.
2. In [docs/decisions.md](../decisions.md) under ADR-004, record LocalJev as an optional wire-level provider candidate alongside Laya, with the decision that its generated probabilities are `calibration_status=unavailable` until S1-owned, artifact-bound calibration evidence exists. Keep S1M training independent of the bridge. Add a note that jev-align is an L4 research/annotation workflow, not a model-runtime dependency.
3. In [docs/s1router/design.md](../s1router/design.md) and the R-001/R-003/R-004/R-005/R-006/R-007/R-008/R-011 acceptance scenarios, add a LocalJev conformance fixture. It should verify `noul`/bool mapping, choice support order, sparse Score mapping, complete output keys, normalization policy, timeout/error mapping, queue saturation, and provenance. The fixture must assert that entropy confidence or a model self-description never authorizes `answered_local`.
4. In [docs/contracts/decision-v1.md](../contracts/decision-v1.md), add an adapter note rather than changing the wire contract: Jev `noul` is an external vocabulary mapped to `bool`; LocalJev's index-based Score is accepted only when the registered task declares the same values; and a bridge that rescales positive-sum vectors must label them raw/unavailable until independently calibrated. Add a conformance test for missing/extra support keys and unregistered task definitions.
5. In [docs/s1m/design.md](../s1m/design.md) and M-003/M-007/M-008 scenarios, document active-learning/prompt optimization as an optional experiment. Require separate optimization labels, holdout labels, and untouched final-test labels; require group/duplicate lineage checks; and state that a jev-align-style 20% holdout does not satisfy the final-test gate when the optimizer searches on the training examples.
6. In [docs/s1m/spec.md](../s1m/spec.md), add a production-capture scenario under M-002/M-012: captured inputs require an approved data class, redaction/consent, bounded retention, access controls, and a clear distinction between disposable observations and release evidence. A capture drop or asynchronous flush must never be presented as a successful audit write.
7. In [docs/engineering/layered-delivery.md](../engineering/layered-delivery.md), add LocalJev to L3 provider fault drills and jev-align-style acquisition/annotation to L4 experiments. Keep L1's remote-disabled/offline invariant. Add an observation field for provider type, model/runner revision, calibration status, queue/retry counts, and whether state crossed a local boundary.
8. In [docs/engineering/delivery.md](../engineering/delivery.md), make upstream code adoption require an immutable source revision, license/NOTICE record, dependency lock update, and separate data/model provenance review. Explicitly forbid using LocalJev's public benchmark results or jev-align's captured inputs as release evidence without new approved inputs and reports.

The first three changes are the smallest useful documentation slice: they make the external projects discoverable, constrain LocalJev to the correct provider role, and prevent confidence/holdout language from weakening the existing S1 contract. Any requirement-ID changes should follow the repository's documented change protocol and be reviewed before hashes are refreshed.

## Recommendation

Use LocalJev as a testable optional adapter target for the L3 remote/local provider boundary after contract conformance and calibration checks. Use jev-align as a source of L4 human-feedback and experiment-management patterns, with its provider calls and reflection path treated as networked research operations. Reuse bounded evaluation, acquisition, persistence, and operator-review ideas; do not promote either repository's defaults, confidence values, holdout metrics, datasets, or model claims to S1 release evidence.
